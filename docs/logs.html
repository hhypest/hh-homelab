Журналы контейнеров

По умолчанию Docker не ротирует журналы вообще: файл растёт, пока на томе не кончится место. В media/compose.yaml у каждого сервиса теперь стоит потолок — 10 МБ на файл, три файла. Здесь разобрано, что именно это значит, как применить, как проверить и что делать с тем, что уже накопилось.

    Раздел 0

    Что происходит без ограничения

    Контейнер пишет в стандартный вывод — Docker перехватывает эти строки и складывает в один файл на томе. Файл этот никем не убирается: ни logrotate DSM, ни сам контейнер о нём не знают. Пока сервис работает, файл только растёт.

    ПараметрПо умолчанию у DockerСтало в медиа-стеке
    driverjson-filejson-file — тот же, просто задан явно
    max-sizeне задан — файл не обрезается никогда10m
    max-fileне задан3 — активный плюс два архива
    Потолок на сервисобъём тома30 МБ
    Потолок на стекобъём тома180 МБ (6 сервисов)
    Почему это не абстрактная предосторожность. Журнал живёт на том же томе, что библиотека и базы приложений. Разросшийся файл отнимает место не у себя, а у Radarr, у базы Jellyfin и у загрузок — и первым симптомом будет не «много логов», а неудачный импорт фильма или база, упавшая в read-only. Уведомление о заполнении тома на 85 % придёт, но объяснит только следствие.
    Home Assistant это уже касалось. В homeassistant/compose.yaml лимиты стояли с самого начала: 10 МБ × 3 у HA и 2 МБ × 2 у dockerproxy. Медиа-стек до сих пор оставался единственным местом в репозитории, где журналы росли свободно.
    Раздел 1

    Что изменилось в compose.yaml

    Правка механическая и одинаковая для всех шести сервисов. Читать её стоит один раз — чтобы понимать, что именно применяется на NAS в следующем разделе.

    1. 1.1 Блок, добавленный каждому сервису

      В media/compose.yaml у qbittorrent, prowlarr, radarr, flaresolverr, jellyfin и seerr появилось одно и то же: 

          networks:
      - media
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"

      Кавычки не для красоты: параметры драйвера — строки. Без них YAML отдаст 3 числом, и дальше как повезёт с версией Compose: одна приведёт к строке молча, другая откажется разбирать файл. Кавычки снимают вопрос — и так же записано в homeassistant/compose.yaml.

    2. 1.2 Что означают 10m и 3суть

      • max-size: "10m" — потолок активного файла. Дойдя до него, Docker переименовывает файл и начинает новый. Суффиксы: k, m, g.
      • max-file: "3" — сколько файлов держать всего, включая активный. То есть активный плюс .1 и .2.
      Считать надо произведение. 10 × 3 = 30 МБ на сервис в худшем случае, 180 МБ на весь стек. Частая ошибка — прочитать max-size как общий лимит и удивиться, что на диске втрое больше.
      Почему именно 10 МБ, а не 1 и не 100. Журнал нужен для разбора аварии, а разбирают её обычно в тот же вечер. 10 МБ текста — это от нескольких часов до нескольких недель истории в зависимости от болтливости сервиса; при 1 МБ ночная серия повторяющихся ошибок вытеснит собственное начало, и причину вы уже не увидите. Три файла дают запас на случай, когда авария случилась вчера, а заметили её сегодня.

    3. 1.3 Почему настройка стоит у каждого сервиса, а не у демона

      Тот же результат даёт log-driver и log-opts в конфигурации демона Docker — тогда лимит достался бы всем контейнерам сразу, включая будущие.

      На DSM этот путь плохой: конфигурация демона принадлежит пакету Container Manager и может быть перезаписана при его обновлении, а сам файл не лежит в этом репозитории — то есть настройка существовала бы только на живом NAS и потерялась бы при переустановке. Строки в compose.yaml версионируются, переезжают вместе с репозиторием и видны в diff.

      Цена решения. Седьмой сервис, добавленный в стек без блока logging, снова будет писать без ограничения. При добавлении контейнера блок нужно копировать — это же относится к Sonarr и Bazarr из дорожной карты.
    Раздел 2

    Применить на NAS

    Настройка журналирования задаётся при создании контейнера. Перезапуск существующего её не подхватит — контейнер нужно пересоздать. Compose делает это сам, увидев изменившийся файл.

    1. 2.1 Забрать изменения на NAS

      cd /volume1/docker/hh-homelab
git pull

      Каталог проекта — /volume1/docker/hh-homelab/media, тот же, что указан в шапке compose.yaml.

    2. 2.2 Проверить файл до применения

      Опечатка в отступе здесь стоит недоступного сервиса, поэтому сначала разбор:

      cd /volume1/docker/hh-homelab/media
docker compose config | grep -A4 logging

      docker compose config печатает конфигурацию так, как её понял Docker. Блоков logging должно быть шесть, в каждом — max-size со значением 10m и max-file со значением 3. Если команда ругается на разбор — правьте YAML, до контейнеров дело ещё не дошло и ничего не сломано.

    3. 2.3 Пересоздать контейнеры

      cd /volume1/docker/hh-homelab/media
docker compose up -d

      Compose сравнит желаемое состояние с текущим, увидит изменившийся LogConfig и пересоздаст все шесть контейнеров: Recreating qbittorrent … done и так далее. Образы не перекачиваются, простой — несколько секунд на сервис.

      Данные при пересоздании не теряются. Всё состояние приложений лежит в томах media/config/<сервис> внутри клона репозитория и в корне библиотеки (MEDIA_ROOT из media/.env), которые монтируются снаружи. Пересоздаётся только сам контейнер — оболочка вокруг процесса. Настройки Radarr, библиотека Jellyfin и активные раздачи qBittorrent остаются на месте.
      Через интерфейс DSM. То же самое делает Container Manager → Проект media → Действие → Собрать. Результат тот же; из SSH просто виднее, что именно произошло.

    4. 2.4 Убедиться, что всё поднялось

      docker compose ps

      Шесть строк в состоянии running. Дальше — обычная проверка живости: открыть Seerr и Jellyfin, убедиться, что раздачи в qBittorrent продолжились.

      Если сервис не поднялся. Смотрите docker compose logs --tail 50 <сервис>. Жалоба на настройку логирования или на размер означает опечатку в max-size — вернитесь к шагу 2.2. Откатиться всегда можно так: убрать блок logging и снова docker compose up -d.
    Раздел 3

    Проверить, что ограничение действует

    Три проверки: настройка записана в контейнер, файл журнала лежит там, где ожидается, и его размер укладывается в потолок.

    1. 3.1 Спросить сам контейнерглавная проверка

      for c in qbittorrent prowlarr radarr flaresolverr jellyfin seerr; do
  printf '%-13s %s\n' "$c" "$(docker inspect --format '{{json .HostConfig.LogConfig}}' "$c")"
done

      Ожидаемый вывод — шесть одинаковых строк:

      qbittorrent   {"Type":"json-file","Config":{"max-file":"3","max-size":"10m"}}
      Пустой Config — значит контейнер не пересоздан. {"Type":"json-file","Config":{}} говорит, что работает старый контейнер, поднятый до правки, и его журнал по-прежнему не ограничен. Помогает docker compose up -d --force-recreate <сервис>.

    2. 3.2 Посмотреть на файлы журналов

      Docker сам скажет, где лежит журнал каждого контейнера — гадать с идентификаторами не нужно: 

      for c in $(docker ps --format '{{.Names}}'); do
  p=$(docker inspect --format '{{.LogPath}}' "$c")
  printf '%-15s %8s  %s\n' "$c" "$(sudo du -sh "$p" | cut -f1)" "$p"
done

      На DSM каталог с журналами — /volume1/@docker/containers/, и заглянуть туда можно только с sudo. Полное дерево с архивами: 

      sudo ls -lh /volume1/@docker/containers/*/*-json.log*

    3. 3.3 Понять, что вы видите

      • Файлов на контейнер — не больше трёх: …-json.log, …-json.log.1, …-json.log.2.
      • Каждый — не больше 10 МБ. Активный обычно меньше: он растёт до порога и только тогда сдвигается.
      • Сразу после пересоздания архивов нет вообще — журнал начат с нуля. Это нормально и означает, что всё сработало.
      Одного прогона мало для полной уверенности. Что ротация действительно происходит, видно только когда сервис наговорит первые 10 МБ. У FlareSolverr и Jellyfin это дни, у Prowlarr — недели. Достаточно вернуться к этой проверке через месяц: если файлов три и все по 10 МБ — механизм работает ровно как задумано, и расти дальше он уже не будет.
    Раздел 4

    Разобрать то, что уже накопилось

    Лимит действует только на новые записи. Хорошая новость: пересоздание контейнеров из раздела 2 уже унесло старые журналы с собой. Этот раздел нужен для контейнеров, которые пересоздавать нельзя или не хочется.

    1. 4.1 Понять, куда делись старые журналысуть

      Журнал принадлежит контейнеру, а не образу и не сервису. Удаляется контейнер — удаляется и его каталог в /volume1/@docker/containers/ вместе со всеми файлами журнала.

      docker compose up -d из шага 2.3 именно это и сделал: старые контейнеры удалены, новые созданы с нуля. Всё, что медиа-стек накопил до правки, освободилось само. Отдельная уборка не нужна — достаточно посмотреть на свободное место до и после.

      Обратная сторона. Вместе с местом пропала и история. Если вы разбирали аварию недельной давности и собирались вернуться к записям — сохраните их до шага 2.3: docker logs qbittorrent > /volume1/homes/…/qb.log 2>&1.

    2. 4.2 Обрезать журнал живого контейнера

      Нужно, когда контейнер трогать нельзя: идёт долгая раздача, Jellyfin отдаёт фильм, или это чужой контейнер вне этого стека. 

      # Обнулить журнал одного контейнера, не останавливая его
sudo truncate -s 0 "$(docker inspect --format '{{.LogPath}}' jellyfin)"

# Все контейнеры разом
for c in $(docker ps -q); do
  sudo truncate -s 0 "$(docker inspect --format '{{.LogPath}}' "$c")"
done

      truncate -s 0 обнуляет длину файла, не трогая сам файл. Открытый у Docker дескриптор остаётся действительным, запись продолжается с начала, перезапуск не нужен.

      Не удаляйте файл журнала через rm. Docker держит его открытым. После rm место не освободится — ядро не отдаст блоки, пока жив дескриптор, — зато docker logs начнёт отдавать пустоту, а сам файл исчезнет из ls. Получается худшее из двух: места нет и журнала нет. Разбирается это только перезапуском контейнера.

    3. 4.3 Не перепутать с журналами приложений

      Docker ограничивает стандартный вывод. Приложения, которые пишут ещё и в собственные файлы внутри тома config, этим лимитом не затронуты вообще:

      СервисСобственные журналыКто их убирает
      Jellyfin/volume1/docker/hh-homelab/media/config/jellyfin/log/сам, по своей политике хранения
      Radarr/volume1/docker/hh-homelab/media/config/radarr/logs/сам, кольцевой набор файлов
      Prowlarr/volume1/docker/hh-homelab/media/config/prowlarr/logs/сам, кольцевой набор файлов
      qBittorrent/volume1/docker/hh-homelab/media/config/qbittorrent/qBittorrent/data/logs/сам, с ограничением из настроек

      Эти каталоги ротируются самими приложениями и обычно невелики. Но если место кончилось, а журналы Docker в норме — искать стоит именно здесь, а заодно в кэше Jellyfin (/volume1/docker/hh-homelab/media/cache/jellyfin), который к журналам отношения не имеет и растёт по своим причинам.

    Раздел 5

    Читать журналы

    Теперь, когда журнал заведомо не длиннее 30 МБ, его стало реально прочитать. Несколько приёмов, которые экономят время при разборе.

    1. 5.1 Смотреть по времени, а не по количеству строк

      # Что происходило за последний час
docker logs --since 1h radarr

# Живой поток, последние 50 строк как контекст
docker logs -f --tail 50 jellyfin

# Окно вокруг известного момента аварии
docker logs --since 2026-08-30T22:00:00 --until 2026-08-30T23:00:00 qbittorrent
      Про --since и ротацию. Docker читает и архивы .1, .2, так что запрос за вчера сработает. Но если сервис за это время наговорил больше 30 МБ, начало окна уже вытеснено — и тогда стоит поднять max-size именно этому сервису, см. раздел 7.

    2. 5.2 Искать по всему стеку сразу

      cd /volume1/docker/hh-homelab/media

# Все шесть сервисов одним потоком, с префиксом имени
docker compose logs -f --tail 20

# Только ошибки за сутки
docker compose logs --since 24h | grep -iE 'error|fatal|exception'

      docker compose logs помечает каждую строку именем сервиса — это единственный способ увидеть, как события в одном контейнере совпадают по времени с событиями в другом. Половина неполадок в конвейере видна только так: Radarr сообщает об ошибке ровно тогда, когда FlareSolverr отдаёт таймаут.

    3. 5.3 Не забывать про --timestamps

      docker logs -t --since 30m seerr

      Не каждое приложение печатает время в собственных строках. Docker знает момент каждой записи и подставит его флагом -t — без этого сопоставить журнал с уведомлением в Пачке или с отметкой в Home Assistant нечем.

      Часовой пояс. -t печатает UTC, а контейнеры живут в Europe/Moscow из TZ. Расхождение на три часа — это не сбой часов, а разница представления; собственные строки приложения при этом московские.
    Раздел 6

    Убавить источник шума

    Ограничение размера — это про следствие. Причина в том, сколько сервис говорит, и её тоже стоит подкрутить: в тихом журнале авария заметна, в болтливом — тонет.

    1. 6.1 FlareSolverr и Seerr — переменной окружения

      У обоих уровень задаётся прямо в compose.yaml и уже стоит в info: 

      environment:
  - LOG_LEVEL=info

      Ставить debug стоит только на время разбора конкретной неполадки — и возвращать обратно. FlareSolverr в отладочном режиме пишет ход каждого обхода защиты Cloudflare и способен выбрать все 30 МБ за вечер активного поиска.

      После правки — пересоздать контейнер. Переменные окружения, как и logging, задаются при создании: docker compose up -d flaresolverr.

    2. 6.2 Radarr и Prowlarr — в веб-интерфейсе

      Settings → General → Logging → Log Level. Рабочее значение — Info. Debug и особенно Trace включают запись каждого обращения к индексаторам: журнал разрастается в десятки раз, а на медленных дисках это ещё и заметная нагрузка.

      Не забыть вернуть. Уровень остаётся в настройках навсегда и переживает перезапуск контейнера. Включённый год назад Trace — довольно частая причина того, что журналы разрослись «сами по себе».

    3. 6.3 Jellyfin — самый болтливый в стеке

      Панель управления → Журналы показывает файлы, а уровень задаётся в каталоге /volume1/docker/hh-homelab/media/config/jellyfin/. Ловушка: образ кладёт туда logging.default.json и перезаписывает его при обновлении. Править нужно копию с именем logging.json — её Jellyfin предпочитает и не трогает. Значение по умолчанию — Information; менять его стоит, только если журнал переполняется за день.

      Откуда объём. Jellyfin пишет строку на каждый запрос плеера, а плеер при перемотке шлёт их пачками. Плюс сканирование библиотеки и разбор метаданных. Отсюда и решение дать ему тот же лимит, что и остальным: 30 МБ хватит примерно на неделю обычного просмотра, а именно неделя и нужна.

    4. 6.4 qBittorrent — отключить лишнее

      Веб-интерфейс на 192.168.3.53:9080, раздел Настройки → Поведение → Файл журнала. Там же, где включается сам файл, задаётся его архивирование и удаление старых копий — это про собственный журнал qBittorrent из шага 4.3, не про журнал Docker.

      Что показывать в Инструменты → Журнал выполнения, выбирается галочками прямо в окне журнала. Категория с сообщениями о пирах на активной раздаче даёт основной поток строк, а для разбора неполадок почти бесполезна.

    5. 6.5 Проверить, что стало тише

      Объективная мера — сколько строк сервис пишет в минуту. Сравните до и после: 

      for c in qbittorrent prowlarr radarr flaresolverr jellyfin seerr; do
  printf '%-13s %s строк за 10 минут\n' "$c" "$(docker logs --since 10m "$c" 2>&1 | wc -l)"
done

      Единицы строк за десять минут — норма для простаивающего стека. Сотни у сервиса, который сейчас ничего не делает, — повод вернуться к его уровню логирования.

    Раздел 7

    Если 10 МБ не подходит

    Значения выбраны как разумная середина, а не как догма. Менять их уместно — важно понимать, что вы покупаете и чем платите.

    1. 7.1 Выбрать значение под задачу

      СитуацияНастройкаПотолок
      Разбираете неполадку, нужна история за недели50m × 5250 МБ на сервис
      Обычная работа — текущий выбор10m × 330 МБ на сервис
      Служебный контейнер, журнал нужен только «на сейчас»2m × 24 МБ — как у dockerproxy
      Журнал не нужен совсемdriver: none0 — и docker logs перестанет работать
      driver: none — почти всегда плохая идея. Он отключает не запись в файл, а сам сбор вывода: docker logs вернёт ошибку, docker compose logs тоже, и разбирать аварию будет нечем. Дешевле поставить 1m × 1: мегабайт места и последние строки перед падением на месте.

    2. 7.2 Изменить и применить

      Правится media/compose.yaml, применяется тем же docker compose up -d — Compose пересоздаст только те сервисы, у которых настройка изменилась. 

      cd /volume1/docker/hh-homelab/media
docker compose config >/dev/null && docker compose up -d

      Первая половина команды проверяет YAML и молчит, если всё хорошо; вторая выполнится только при успешной проверке. Дальше — раздел 3, проверка через docker inspect.

      Правка должна попасть в репозиторий. Рабочее дерево на NAS и есть клон репозитория, так что git status сразу покажет изменение. Незакоммиченная правка потеряется при следующем git pull.

    Проверить настройку контейнераdocker inspect --format '{{json .HostConfig.LogConfig}}' radarr
    Найти файл журналаdocker inspect --format '{{.LogPath}}' radarr
    Размер всех журналовsudo du -ch /volume1/@docker/containers/*/*-json.log*
    Обнулить журнал живого контейнераsudo truncate -s 0 "$(docker inspect --format '{{.LogPath}}' radarr)"
    Последний часdocker logs --since 1h radarr
    Живой поток со временемdocker logs -f -t --tail 50 radarr
    Весь стек одним потокомdocker compose logs -f --tail 20
    Ошибки за сутки по всему стекуdocker compose logs --since 24h | grep -iE 'error|fatal'
    Сохранить журнал в файлdocker logs radarr > ~/radarr.log 2>&1
    Применить изменённый composedocker compose up -d
    Все команды выполняются по SSH на NAS. Для тех, что читают /volume1/@docker, нужен sudo: каталог принадлежит root, и это правильно — в журналах бывают ключи и токены, попавшие туда из сообщений об ошибках.

    СимптомПричинаЧто делать
    LogConfig пустой у одного сервиса Контейнер не пересоздан — например, поднят вручную мимо Compose docker compose up -d --force-recreate <сервис>, шаг 3.1
    Файл журнала больше 10 МБ Контейнер создан до правки; лимит применяется к новым записям, а не задним числом Пересоздать контейнер либо обрезать, шаг 4.2
    Место на томе не освободилось после уборки Файл удалён через rm, дескриптор ещё открыт у Docker Перезапустить контейнер; впредь truncate -s 0, шаг 4.2
    Контейнер не стартует после правки Значение без кавычек или неверный суффикс в max-size docker compose config, шаг 2.2
    docker logs ничего не отдаёт У сервиса выставлен driver: none или журнал только что обнулён Проверить LogConfig, шаг 3.1
    Журналы Docker в норме, а место кончается Растут собственные файлы приложений или кэш Jellyfin Шаг 4.3
    История за вчера уже вытеснена Сервис говорит больше 30 МБ в сутки Убавить уровень логирования (раздел 6) или поднять лимит (раздел 7)
