# Keenetic Hopper SE (KN-3812) — что делать и чего НЕ делать

Разобрано по вашему selftest от 29.08.2026 (KeeneticOS 5.02.A.6.00, hostname `serv`).

## Текущая картина

| Сегмент | Интерфейс | Подсеть | Уровень | Кто там живёт |
|---|---|---|---|---|
| Home | `Bridge0` (Vlan1 + Wi-Fi 5 ГГц `hhHome`) | 192.168.3.0/24 | private | hhNAS `.53`, hhTV `.52`, hhPC `.50`, hhPhone `.51` |
| IoT | `Bridge1` (Vlan2 + Wi-Fi 2,4 ГГц `hhIoT`) | 10.0.50.0/24 | protected | Alice `10.0.50.50`, hhIR, lwip0–3, Cleaner, Frozen |

Ключевое из конфигурации:

- `isolate-private` — сегменты изолированы друг от друга. **Оставляем как есть.**
- `ip policy Policy0` («Def»): `permit global Wireguard0`, `no permit global ISP`.
  Политика назначена **обоим** сегментам и поимённо всем хостам, включая
  `AA:BB:CC:11:22:33` (hhNAS). То есть весь трафик NAS уходит в туннель
  «VPN».
- `ip name-server 10.0.0.53 "" on Wireguard0` — единственный DNS доступен
  только через туннель.
- `mdns reflector disable` — mDNS между сегментами не ретранслируется.
  Для нас это неважно: Home Assistant и телевизор в одном сегменте.
- `ip http proxy nas` — KeenDNS уже опубликован на DSM (`5001`).

## Что менять НЕ нужно

Управление телевизором через Алису идёт по маршруту
«колонка → облако Яндекса → навык Yaha Cloud → Home Assistant», то есть
**наружу**, а не между сегментами. Ни одного правила межсетевого экрана
для этого добавлять не требуется. Изоляция 192.168.3.0/24 ↔ 10.0.50.0/24
сохраняется полностью.

## Что проверить перед настройкой (5 минут)

Весь исходящий трафик NAS идёт через WireGuard. Пачка, Яндекс и GitHub
могут по-разному относиться к зарубежным или дата-центровым IP.
Подключитесь по SSH к DSM и проверьте:

```bash
# Через какой внешний адрес нас видит мир
curl -s https://api.ipify.org ; echo

# Пачка — нужен любой ответ, кроме таймаута
curl -sS -o /dev/null -w 'pachca: %{http_code}\n' https://api.pachca.com/api/shared/v1/

# Облако Yaha (навык для Алисы)
curl -sS -o /dev/null -w 'yaha:   %{http_code}\n' https://yaha-cloud.ru/

# GitHub — нужен для установки HACS и компонента Yandex Smart Home
curl -sS -o /dev/null -w 'github: %{http_code}\n' https://github.com/
```

Если что-то не отвечает — варианты по возрастанию радикальности:

**1. Точечный маршрут в обход туннеля.** Веб-интерфейс роутера →
*Интернет → Маршрутизация → Добавить маршрут*: «Маршрут до узла»,
адрес — IP нужного сервиса, интерфейс — «Провайдер (ISP)».
В CLI это выглядит так:

```
ip route <IP-узла> 255.255.255.255 ISP auto
```

Минус: у облачных сервисов IP меняются.

**2. Отдельная политика для NAS.** *Интернет → Приоритеты подключений* →
создать политику «Прямое подключение» с единственным подключением ISP →
на вкладке устройств назначить её `hhNAS`. Тогда NAS ходит напрямую,
а остальная сеть остаётся в туннеле.
Учтите: Prowlarr и qBittorrent тоже перестанут пользоваться VPN.

**3. Резервный DNS.** Сейчас единственный сервер имён `10.0.0.53`
доступен только через `Wireguard0`. Если туннель упадёт, разрешение имён
встанет во всей сети. Добавьте запасной сервер на интерфейсе провайдера:

```
ip name-server 77.88.8.8 "" on ISP
ip name-server 1.1.1.1 "" on ISP
```

В интерфейсе: *Интернет → Проводной → Настройка DNS → Добавить сервер DNS*.

## Опционально: внешний доступ к Home Assistant через KeenDNS

У вас уже настроен KeenDNS для DSM. Добавим второе приложение — HA.

Веб-интерфейс: *Управление → Доменное имя → раздел «Приложения» →
Добавить приложение*:

- Название: `ha`
- Адрес сервера: `192.168.3.53`
- Порт: `8123`
- Протокол: HTTP
- Авторизация роутера: **выключить** (у Home Assistant своя, а мобильное
  приложение HA не умеет проходить басик-авторизацию Keenetic)

Эквивалент в CLI (`telnet 192.168.3.1 2023` или SSH на порт 2022):

```
ip http proxy ha
    upstream http 192.168.3.53 8123
    domain ndns
    ssl redirect
    security-level public
!
system configuration save
```

После этого:

1. В `secrets.yaml` заполните `ha_external_url` реальным адресом.
2. В `configuration.yaml` раскомментируйте строку `external_url`.
3. Секция `http:` уже содержит `use_x_forwarded_for: true` и
   `trusted_proxies: 192.168.3.1` — без них Home Assistant увидел бы все
   запросы как приходящие от роутера и после пяти неудачных входов
   заблокировал бы его целиком.

## Диагностика, если что-то не находится

```
# На роутере: увидеть арендованные адреса и понять, кто есть кто
show ip dhcp bindings

# Проверить, что телевизор жив и виден в домашнем сегменте
ping 192.168.3.52

# Убедиться, что колонка НЕ доступна из домашнего сегмента (так и задумано)
# С NAS: ping 10.0.50.50 → должен молчать
```
