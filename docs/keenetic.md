# Роутер: что важно для этого стека

Шлюз сети — Keenetic. Ниже то, что влияет на работу Home Assistant и медиа-стека,
без инвентаря устройств: конкретные имена, адреса и параметры туннеля живут
в локальной копии этого файла, а не в публичном репозитории.

> Если ведёте свои заметки по сети — назовите файл `docs/keenetic.local.md`,
> он перечислен в `.gitignore` и в git не попадёт.

## Два сегмента

| Сегмент | Подсеть | Уровень доступа | Кто там |
|---|---|---|---|
| Home | `192.168.3.0/24` | private | NAS, телевизор, приставка, рабочие устройства |
| IoT | `10.0.50.0/24` | protected | умная колонка, датчики, бытовая техника |

Включена изоляция домашних сегментов (`isolate-private`): устройства из IoT
не видят домашний сегмент, и наоборот. **Эта конфигурация её не нарушает
и не требует ни одного правила межсетевого экрана.**

Причина в маршруте голосовой команды: колонка отдаёт её в облако Яндекса,
облако возвращает в Home Assistant по исходящему соединению NAS. Трафик идёт
наружу и обратно, а не между сегментами.

Ретрансляция mDNS между сегментами выключена — и не нужна: Home Assistant,
телевизор и приставка живут в одном сегменте, обнаружение по SSDP работает
внутри него.

## Если весь трафик идёт через VPN

Распространённая конфигурация: политика подключений отправляет весь исходящий
трафик в WireGuard-туннель. Тогда стоит проверить, что нужные сервисы вообще
отвечают — некоторые по-разному относятся к зарубежным и дата-центровым
адресам.

По SSH на NAS:

```bash
# Каким адресом нас видит мир
curl -s https://api.ipify.org; echo

# Пачка — нужен любой ответ, кроме таймаута
curl -sS -o /dev/null -w 'pachca: %{http_code}\n' https://api.pachca.com/api/shared/v1/

# Облако Yaha — навык Умного дома для Алисы
curl -sS -o /dev/null -w 'yaha:   %{http_code}\n' https://yaha-cloud.ru/

# GitHub — нужен для HACS и сторонних компонентов
curl -sS -o /dev/null -w 'github: %{http_code}\n' https://github.com/
```

Если что-то молчит — три варианта по возрастанию радикальности.

**Точечный маршрут в обход туннеля.** *Интернет → Маршрутизация → Добавить
маршрут*: «Маршрут до узла», адрес сервиса, интерфейс «Провайдер». В CLI:

```
ip route <IP-узла> 255.255.255.255 ISP auto
```

Минус очевиден: у облачных сервисов адреса меняются.

**Отдельная политика для NAS.** *Интернет → Приоритеты подключений* → создать
политику с единственным подключением ISP → назначить её NAS. Учтите: Prowlarr
и qBittorrent тоже выйдут из-под VPN, а для них он обычно и нужен.

**Резервный DNS.** Если единственный сервер имён объявлен только на интерфейсе
туннеля, падение туннеля останавливает разрешение имён во всей сети. Стоит
добавить запасной на интерфейсе провайдера:

```
ip name-server 77.88.8.8 "" on ISP
ip name-server 1.1.1.1 "" on ISP
```

В интерфейсе: *Интернет → Проводной → Настройка DNS → Добавить сервер DNS*.

## Проброс порта для раздачи

qBittorrent слушает `6881/tcp` и `6881/udp`. Если весь трафик NAS идёт через
VPN-туннель, входящие подключения на этот порт до него не дойдут: у туннеля
нет проброса, если провайдер его не даёт отдельной опцией.

Практическое следствие: раздача работает только на тех пиров, к которым
qBittorrent подключился сам. Рейтинг растёт медленнее, но клиент не «сломан».
Если у VPN-провайдера есть port forwarding — пробросьте на нём тот же порт
и укажите его в настройках соединения qBittorrent.

## Внешний доступ через KeenDNS

Keenetic умеет публиковать внутренние веб-приложения наружу через свой
реверс-прокси: *Управление → Доменное имя → Приложения → Добавить*.

Для Home Assistant: адрес сервера `192.168.3.53`, порт `8123`, протокол HTTP,
авторизацию роутера **выключить** — у Home Assistant своя, а мобильное
приложение не умеет проходить базовую авторизацию Keenetic.

Секция `http:` в `configuration.yaml` к этому уже готова: там прописаны
`use_x_forwarded_for: true` и `trusted_proxies` с адресом роутера. Без них
Home Assistant видел бы все запросы приходящими от роутера и после пяти
неудачных попыток входа заблокировал бы его целиком — вместе со всем внешним
доступом.

> Взвесьте, что именно публикуете. Панель управления NAS, опубликованная
> наружу, — это сервис аутентификации, доступный всему интернету. Для доступа
> к файлам и настройкам NAS безопаснее поднять VPN на самом роутере, а через
> KeenDNS публиковать только то, что действительно нужно снаружи.

## Диагностика

```
# На роутере: кто какой адрес получил
show ip dhcp bindings

# Телевизор жив и виден в домашнем сегменте
ping 192.168.3.52

# Колонка НЕ доступна из домашнего сегмента — так и задумано.
# С NAS: ping <адрес колонки> должен молчать.
```
