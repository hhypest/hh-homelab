    1.1.0

    Перенос, маршрутизация, лицензии и первое обновление образов

    18 сентября 2026. Две с половиной недели после первого выпуска ушли не на новые сервисы, а на то, чтобы обжить собранное: описать перенос стека на чужое железо, разобрать маршрутизацию и DNS на роутере, привести в порядок лицензирование и закрыть проверками то, что до сих пор держалось на внимательности. Под конец подняты версии шести образов из девяти — первое обновление с момента закрепления, и среди них Jellyfin с необратимой миграцией базы.

    Что поменяется на работающем сервере. Во-первых, версии: шесть образов из девяти подняты, и очередной docker compose up -d заменит шесть работающих приложений — состав и оговорки в разделе «Состав выпуска». Во-вторых, четыре правки в конфигурации: из configuration.yaml убрана секция http: целиком — Home Assistant перестал её читать, настройки переехали в интерфейс (разбор ниже); в media_tv.yaml переделана связка телевизора с приставкой; в шаблонах Home Assistant исправлено экранирование в регулярных выражениях; в шаблоне Jellyfin для Пачки DirectStream больше не выдаётся за прямое воспроизведение. Всё остальное — документация, тесты и CI, и на работающий сервер не влияет.

    Состав выпуска

    Что чинится этим обновлением. В Prowlarr — пустые cookie от FlareSolverr и редиректы 307/308 при скачивании с индексатора; в FlareSolverr — получение cookie до истечения задержки waitInSeconds. Две половины одной и той же болячки, и обе стоит забрать вместе. В Radarr, кстати, починена совместимость с Jellyfin 12 — это пригодится, когда дойдём до него.
    Индексаторы Prowlarr могли переехать. В 2.6 убран MoreThanTV (сайт закрылся), FunFile переведён на Cardigann, у нескольких трекеров поменялись категории. Русских трекеров из вашего набора это не касается, но если список индексаторов после обновления выглядит иначе — причина здесь, а не в поломке.

    Переход на Jellyfin 12

    Номер выглядит как прыжок через мажор, но это не он: Jellyfin выкинул ведущую «10.» из схемы версий, и то, что должно было называться 10.12, называется 12. По существу это один функциональный выпуск вперёд, а не два.

    Откатиться нельзя. Дословно из релиза 12.0: «this release includes database changes that prevent rolling back without a full restore». Миграция базы необратима — вернуться можно только полным восстановлением каталога данных из копии. Поэтому копия снимается не «на всякий случай», а как обязательный шаг, и снимается свежая: задание Hyper Backup из шага 10.1 могло отработать вчера.

    Прямое обновление поддержано с 10.10.7 и с любой 10.11.x. Вы на 10.11.11 — путь есть, промежуточных остановок не нужно.

    Порядок

    Порядок здесь не косметический. Плагины снимаются через панель работающего Jellyfin 10.11 — то есть до остановки контейнера и до up -d с новым образом. Если запустить 12 со сторонними плагинами на месте, миграция пойдёт ровно так, как релиз просит не делать, а отменить её будет нельзя. Поэтому контейнер здесь останавливается и запускается дважды: это не описка.

    1. Сохранить настройку вебхука. Контейнер пока работает, файл просто копируется рядом:

    cd /volume1/docker/hh-homelab/media
sudo cp -a config/jellyfin/plugins/configurations/Jellyfin.Plugin.Webhook.xml \
  config/jellyfin.webhook.xml
    Шаблон-то в репозитории есть — pachca/payloads/jellyfin.handlebars, — а вот адрес вебхука Пачки нет и быть не может: это секрет, его вычищает проверка обезличивания. Живёт он только в этом XML, и восстановить его потом будет неоткуда.

    2. Снять копию. Контейнер остановить — база SQLite на ходу копируется неконсистентно, — скопировать каталог состояния и запустить обратно:

    sudo docker compose stop jellyfin
sudo cp -a config/jellyfin config/jellyfin.10.11.backup
du -sh config/jellyfin.10.11.backup
sudo docker compose start jellyfin
    Последняя строка не лишняя. Jellyfin нужен работающим для следующего шага: плагины снимаются из его панели. Копия при этом снята с полностью рабочей 10.11 — если миграция не заладится, восстановление вернёт систему целиком, вместе с плагинами.
    Кэш копировать не нужно — cache/jellyfin это метаданные, они пересоберутся. Копия нужна только с config/: там база, настройки, пользователи и профили устройств.

    3. Снять сторонние плагины. Панель → Плагины, удалить всё, что не входит в поставку, — как минимум Webhook. Из релиза: «Installed repository plugins (anything not built-in) should also be removed before migrating». Останавливать контейнер после этого не нужно: up -d на следующем шаге сам пересоздаст его с новым образом.

    4. Обновиться.

    cd /volume1/docker/hh-homelab
git pull
cd media
sudo docker compose pull jellyfin
sudo docker compose up -d jellyfin
sudo docker compose logs -f jellyfin
    Первый запуск будет долгим, и это нормально. Идёт миграция базы, а следом сплошная проверка путей по всей библиотеке: «First scan will take significantly longer than normal». Не перезапускайте контейнер посреди этого. Смотрите в журнал: пока строки идут — работа идёт.

    5. Вернуть Webhook. Панель → Плагины → Каталог, поставить Webhook версии 22 или новее из официального репозитория, перезапустить контейнер. Дальше — Add Generic Destination: адрес из сохранённого XML, шаблон из pachca/payloads/jellyfin.handlebars, типы уведомлений как были.

    Совместимость проверена. У версии 22 targetAbi: 12.0.0.0 — это первая версия под 12.x, — и все двадцать переменных вашего шаблона — от Video_0_Codec и Audio_0_Channels до PlayMethod и PlayedToCompletion — на месте. Обратная сторона: v22 не встанет на 10.11, так что порядок «сначала сервер, потом плагин» обязателен.

    6. Прогнать библиотеку. Панель → Библиотеки → Сканировать все библиотеки. Полное сканирование в 12.0 обязательно: оно восстанавливает альтернативные версии файлов.

    HTTP переехал из YAML в интерфейс

    После разворачивания Home Assistant показал предупреждение: «The HTTP configuration in configuration.yaml has already been migrated and is now being ignored». Это не поломка и не следствие наших правок: начиная с версии 2026.8 Home Assistant не читает секцию http: из configuration.yaml. При первом запуске он переносит её содержимое в интерфейс и заводит напоминание в Settings → System → Repairs — убрать блок из файла.

    Блок убран. Оставлять его было бы хуже, чем убрать: он ничего не ломает, но молча игнорируется, а правка в нём выглядит как настройка и ни на что не влияет. Настройки живут теперь в Settings → System → Network, раздел HTTP server.

    Граница восстановления сдвинулась, и не нами. Настройки HTTP перестали быть частью репозитория: они уехали в config/.storage/, а этот каталог в .gitignore — там же токены и учётные записи. Значит, клон на новой машине поднимется с настройками по умолчанию, и блокировка по IP окажется выключенной. Раньше это гарантировала строка в файле под контролем версий; теперь гарантировать нечем, кроме проверки руками.

    Отсюда новый шаг 2.7 в чек-листе Home Assistant: сверить по списку то, что раньше сверялось файлом.

Оно было принято в этом же выпуске и остаётся в силе — поменялось только место, где оно записано: не строка в configuration.yaml, а переключатель в интерфейсе. Объяснение, зачем так, осталось в configuration.yaml комментарием на месте убранного блока: файл читают чаще, чем историю версий, и вопрос «а где HTTP?» возникает именно там.

    Перенос на другое железо

    Появилась девятая страница — «Другие платформы». Первый выпуск честно говорил, что проверен на DS725+, но не говорил, что именно к этой машине привязано. Теперь привязанное сведено в реестр из четырёх таблиц: где стоит адрес NAS, где PUID синологичного пользователя, где профиль качества под конкретный телевизор, где маршрутизация под конкретного провайдера — и чем это заменяется на другом железе.

    Там же описан путь без Docker: тот же набор сервисов пакетами SynoCommunity. Он не заменяет основной и заведён для тех, кому Docker на NAS недоступен или не нужен; единственный пробел — FlareSolverr, пакета для него нет.

    Переезд со старой схемы абсолютных путей убран. Шаг 2.6 чек-листа медиа-стека и строка в README, которая на него ссылалась, удалены: схема с абсолютными путями отжила, а инструкция по миграции с неё только сбивала с толку тех, кто ставит стек с нуля.

    Роутер: маршрутизация и DNS

    Страница роутера выросла в полтора раза и стала отдельным разбором, а не приложением к чек-листу. Главное в ней — три сюжета, каждый из которых начинался с симптома, выглядевшего как поломка не там, где она была:

    • Подпись DPI в журнале. «SSL connection could not be established» и сброс соединения сразу после ClientHello — это не сломанный сертификат и не упавший сервис, а обрыв по имени узла. Рядом — набор правил для трекеров и ловушка с именем анонсера, которая тихо убивает раздачу;
    • DNS — задача, отдельная от маршрутизации. Провайдер отвечает на заблокированный домен адресом-заглушкой, и соединение, уже уехавшее в туннель, приходит в никуда. Разобрано, чем route отличается от evaluate: первое завершает разбор правил и вместе с ним убирает запасной путь, второе — нет. Пока туннель жив, разницы не видно; когда сервер имён за route замолкает, это выглядит как «пропал интернет у всего, что ходит через туннель»;
    • Красная кнопка Test у FlareSolverr — не поломка прокси. Prowlarr проверяет её походом на prowlarr.servarr.com, и красный крест означает недоступность этого адреса, а не решателя.

    Внешний доступ: туннель вперёд публикации

    Раздел про внешний доступ переписан: сначала VPN-сервер на роутере, потом публикация через KeenDNS. Порядок содержательный — опубликованное веб-приложение это страница входа, открытая всему интернету, а VPN-сервер на неверный ключ просто молчит.

    Изменение конфигурации. Из configuration.yaml убраны use_x_forwarded_for и trusted_proxies. Обе строки осмысленны, только пока перед Home Assistant стоит обратный прокси; при доступе через туннель его в цепочке нет, а включённое «про запас» доверие к заголовку X-Forwarded-For позволяет подменить адрес клиента и обойти счётчик неудачных входов, на котором держится ip_ban_enabled. На их месте в файле стоит комментарий, объясняющий, когда и как их вернуть — обе разом, поодиночке Home Assistant их не примет.
    Если вы публиковали HA через KeenDNS — после git pull верните обе строки, иначе Home Assistant увидит все запросы приходящими от роутера и после пяти неудачных попыток входа заблокирует его целиком, вместе со всем внешним доступом.

    Лицензии: код и текст разведены

    Репозиторий на девять десятых состоит из прозы, а лежал целиком под MIT — лицензией, в которой всё называется словом «Software». Теперь разведено: код остаётся под MIT, страницы в docs/ и README уходят под CC BY 4.0. Команды и фрагменты конфигурации внутри страниц — тоже MIT, и это главное, ради чего разделение и сделано: команду из чек-листа вставляют к себе в терминал, требовать за это указания авторства нелепо.

    GitHub не видел лицензию вовсе. К тексту MIT в LICENSE было дописано примечание по-русски, и детектор перестал узнавать в файле лицензию: API отдавал по репозиторию "license": "other", NOASSERTION. Бейдж в README обещал MIT, страница репозитория показывала «Other». LICENSE теперь голый текст MIT, примечание переехало в NOTICE.md и там же разрослось.

    Заодно сверены все лицензии стороннего ПО — с первоисточниками, а не по памяти. Нашлись две ошибки: VueTorrent (GPL-3.0) стоял в DOCKER_MODS у qBittorrent, но в перечне отсутствовал, а Monitor Docker числился под MIT, хотя он Apache-2.0. Уточнено и про qBittorrent: исходники GPL-2.0-or-later, сборки GPL-3.0-or-later, исключение для OpenSSL.

    У образа и у программы внутри лицензии разные. Пять сервисов приезжают в образах linuxserver.io, и обвязка вокруг приложения — базовый слой, s6-overlay, работа с PUID — распространяется под GPL-3.0 независимо от того, под чем лежит само приложение. Jellyfin — GPL-2.0, образ с Jellyfin — GPL-3.0. Раньше этого различия в перечне не было.

    Появились NOTICE.md (что под какой лицензией, перечень стороннего ПО, правило цитирования текста, оговорки) и CONTRIBUTING.md (правка приходит на тех же условиях, что и остальной репозиторий). В оговорки добавлено то, чего не было: ответственность за скачиваемое лежит на пользователе, законность зависит от юрисдикции, и ни один разбор в документации не является юридической консультацией. Каждая страница теперь подписана в подвале: текст под CC BY держится на указании авторства, а страницу сохраняют и пересылают в отрыве от репозитория.

    Dependabot: образы молчали две недели

    Экосистема docker-compose заведена 2 сентября, расписание еженедельное — и ни одного пул-реквеста, хотя обновления были: Jellyfin, Radarr, Prowlarr, FlareSolverr и Home Assistant успели уйти вперёд. При этом сам Dependabot жив: по pip и github-actions он завёл восемь PR в конце августа.

    Проверено по первоисточникам — и не подтвердилось ничего:

    ПодозрениеЧем провереноИтог
    Неверное имя экосистемытаблица значений package-ecosystem в справочнике GitHub docker-compose — верное
    compose.yaml не подходит под искомые имена FILENAME_REGEX из dependabot-core подходит
    directories не поддерживается справочникподдерживается
    Реестр lscr.io не опрашивается запрос к /v2/…/tags/list это псевдоним ghcr.io, отвечает
    Нужных тегов нет в реестре постраничный обход всех 4511 тегов Home Assistant 2026.9.2 на месте
    Ложный след — граф зависимостей. На вкладке Dependency graph → Dependabot compose-файлов нет, и это выглядит как улика. Не улика: Docker и Docker Compose в граф зависимостей не входят вовсе — там только Bazel, Cargo, Composer, Deno, NuGet, Actions, Go, Gradle, Julia, Maven, npm, OpenTofu, pip, pnpm, pub, Poetry, RubyGems, Swift и Yarn. Образов там не бывает ни у кого, и SBOM репозитория их тоже не покажет.

    Осталась одна конструкция, которой не было в двух работающих блоках, — directories во множественном числе. Блок разбит на два с directory, чтобы её исключить. Это проверка гипотезы, а не известное лекарство: если PR не появятся и теперь, дело не в ней. Побочный эффект полезен сам по себе — Dependabot перечитывает конфиг при каждом push в основную ветку, так что ответ придёт за минуты, а не через неделю.

    Два PR вместо одного здесь безопасны. Прежняя беда — когда ветки от одного старого main откатывают правки друг друга — случается, только если пул-реквесты трогают один и тот же файл. Эти два не пересекаются: у каждого свой compose.yaml.
    Не помогло. После слияния Dependabot перечитал конфиг — его собственный валидатор дал success, — но прогона по образам не поставил ни через семнадцать минут, ни через тридцать восемь. Гипотеза с directories закрыта: дело не в ней.
    Чем кончилось. Экосистема docker-compose убрана из .github/dependabot.yml. Причина молчания так и осталась неизвестной, но держать настройку, которая не работает и создаёт ложное чувство, что за версиями кто-то следит, — хуже, чем не держать её вовсе. Обращаться в поддержку GitHub не стали: сверка с реестром решает задачу целиком и не зависит ни от кого. Для действий GitHub и пакетов Python Dependabot работает и остался — восемь его пул-реквестов в репозитории тому подтверждение.
    Что от этого выиграли. Dependabot не умел читать DOCKER_MODS в принципе — мод VueTorrent был вне его поля зрения с самого начала, и в документации на это стояла отдельная оговорка. Своя сверка читает его наравне с ключом image, так что оговорка больше не нужна: все девять образов проверяются одинаково.

    Сверка образов, не зависящая от Dependabot

    Отсюда следует вывод, который стоило сделать раньше: закрепление версий держится на том, кто приносит обновления, и этот кто-то может молча перестать приходить. Появился scripts/check_image_updates.py — он читает оба compose-файла вместе с DOCKER_MODS, ходит в реестр и говорит, что отстало. В CI его нет намеренно: это поход в сеть наружу, ему не место в проверке на каждый push.

    Как решается, что тег новее. Теги здесь непохожи на semver: 5.2.3_v2.0.14-ls474, 10.11.11ubu2604-ls47. Сравнивать их как строки бессмысленно, угадывать структуру опасно. Поэтому у тега берётся форма — все цифры заменяются на N, — и сравниваются только теги одинаковой формы, по кортежу чисел в них. Ночные сборки, ветки develop и беты отсеиваются при этом сами: у них другая форма, и отдельного фильтра для них не нужно.
    Случай, ради которого сделано исключение. Jellyfin выкинул ведущую «10.» из схемы версий, и 10.11.11ubu2604-ls47 превратился в 12.1ubu2604-ls50. Форма разная — ранжировать машине нельзя, но и промолчать нельзя: это самое важное обновление из всех. Такие теги попадают в отдельный раздел «форма тега изменилась», без вердикта. Отличаются они по скелету — форме без учёта того, сколько в версии числовых частей: у обоих тегов это .ubu-ls. Заодно скелет отсекает похожее по числам, но чужое по природе: у sha-8253831 он sha-, у 3.4-pr-186 — .-pr-. До этого уточнения в раздел «смотреть» попадали четыре образа из девяти вместо одного.

    Разбор образов перестал существовать в двух экземплярах: функция images() теперь лежит в скрипте, а tests/test_compose_images.py берёт её оттуда. Список, который проверяется на плавающие теги, и список, который сверяется с реестром, обязаны быть одним и тем же.

    Что ещё

    • Медиа-стек. Свои определения индексаторов (шаг 5.3) с разбором формата и предупреждением читать YAML перед установкой: в нём записано, как логиниться на трекер. Разбор DTS вместо одной строки в скобках. Ограничение скорости раздачи. Отчёт о возможностях приставки — шаг 7.6;
    • Телевизор и приставка. Связка включается от телевизора, а не от приставки, и научилась различать, кто из двух не проснулся;
    • Пачка. DirectStream перестал выдаваться за прямое воспроизведение — это перепаковка контейнера, и в уведомлении она теперь названа своим именем;
    • Wi-Fi. Разбор WPA3 Personal и почему DPP не построен поверх SAE;
    • Экранирование в шаблонах. В фильтрах вида search('^sensor\.docker_') одинарный обратный слэш съедался разбором YAML, и точка в выражении означала «любой символ» вместо точки. Теперь слэш удвоен, а validate_config.py компилирует шаблоны и такое ловит;
    • Граница восстановления записана явно: что вернётся из клона, а что придётся заводить руками.
    Что сломалось в самом выпуске. Таблица версий в описании релиза собирается из compose-файлов, и в 1.1.0 в неё попала строка | , | , |. Сборка была однострочником в workflow — grep искал image: в любом месте строки, а в media/compose.yaml есть комментарий со словами «он ищет поля image:, а здесь»: запятую после двоеточия и приняли за образ. Комментарий, объясняющий слепое пятно Dependabot, угодил в слепое пятно сборщика описаний. Текст релиза на GitHub поправлен вручную, сообщение тега v1.1.0 оставлено как есть — переставлять опубликованный тег ради строки в описании дороже, чем она стоит. Сам разбор вынесен в scripts/release_images.sh и сверяется тестом с разбором через pyyaml из scripts/check_image_updates.py: теперь у описания выпуска и у сверки версий один список образов на двоих. Исправление войдёт в следующий выпуск — в 1.1.0 его нет.
    1.0.0

    Первый выпуск

    2 сентября 2026. Домашний сервер на Synology DS725+ собран, описан и закрыт проверками. Версия 1.0 фиксирует не только файлы конфигурации, но и то, что реально работает: все образы закреплены на конкретных тегах, так что клон этого тега поднимет ту же систему, а не «примерно такую же».

    Что это

    Два независимых compose-проекта на одном NAS. Медиа-стек — шесть контейнеров, превращающих запрос в Seerr в фильм в библиотеке Jellyfin без единого лишнего копирования по диску. Home Assistant — метрики NAS и контейнеров, уведомления в Пачку, управление телевизором и приставкой, голосовые сценарии через Алису.

    Клон репозитория и есть рабочая конфигурация: оба стека монтируют своё состояние относительными путями, поэтому весь сервер переносится вместе с репозиторием, а правки видны в git status сразу.

    Состав выпуска

    Версии получены сверкой дайджестов: для каждого образа взят дайджест плавающего тега и найден версионный тег, ведущий на тот же самый образ. То есть закреплено ровно то, что работало на момент выпуска.

    Что вошло

    Медиа-стек. Шесть контейнеров в общей bridge-сети. Импорт хардлинком вместо копирования: файл в библиотеке и раздающийся торрент — одни и те же данные, место занято один раз, раздача не прерывается. Профиль качества под конкретный телевизор, чтобы не тащить 4K на панель 1366×768.

    Home Assistant. Метрики NAS через интеграцию Synology DSM, метрики контейнеров — через docker-socket-proxy, который пропускает только чтение: сам сокет в HA не пробрасывается, потому что доступ к нему равносилен root на NAS. HTTP-проверки живости каждого сервиса, статистика простоя, уведомления в Пачку с разделением по чатам.

    Уведомления. Пять ботов, два чата: в одном то, что смотреть, в другом то, что чинить. Liquid-шаблоны на каждый сервис лежат в репозитории и проверяются локально на сохранённых примерах payload, а не «дождёмся настоящего события».

    Телевизор и приставка. Wake-on-LAN, сценарии просмотра, голосовое управление через Алису по облачному подключению. Отдельно разобрано, почему телевизор остаётся на кабеле: WoL по Wi-Fi требует WoWLAN, которого у этой модели нет.

    Конфигурация вынесена в .env. Репозиторий публичный, и всё, что относится к конкретной машине — права, часовой пояс, корень библиотеки, адрес привязки, имя сети и порты, — живёт в файле рядом с compose. Значений по умолчанию нет намеренно: забытый .env роняет запуск с внятным сообщением, а не поднимает стек с пустыми значениями.

    Восемь задач проверок в CI и 146 тестов. Проверяется не только синтаксис: список контейнеров под надзором сверяется с compose-файлами, каждый entity_id — с тем, кто его создаёт, переменные — с образцом .env.example, порты, по которым Home Assistant опрашивает сервисы, — с ним же, счётчики шагов в README — с самими страницами, а образы — с требованием иметь закреплённую версию. Каждая такая проверка появилась после случая, когда что-то разошлось молча.

    Выпуски делает workflow, а не человек в терминале. Тег, релиз и его описание собираются одной кнопкой, с отказом на невнятной версии, повторном теге, неописанной версии и любой упавшей проверке. Подробнее ниже, в разделе «Как выпускается версия».

    Восемь страниц документации с отметками о прогрессе: два чек-листа развёртывания, гайд по журналам, обзор проекта, справочник по уведомлениям, заметки по роутеру, дорожная карта и эта страница. Обезличивание проверяется автоматически — MAC-адреса, имена устройств и имя точки доступа в публичный репозиторий не попадают.

    Известные ограничения

    ЧтоПочему так
    Транскодирование только программноеу Ryzen R1600 нет встроенной графики, аппаратного кодировщика в DS725+ физически нет. Один поток 1080p забирает оба ядра почти целиком

    Падение самого NAS никто не заметитвсё, что шлёт уведомления, работает на нём же. Внешний пульс — третий пункт дорожной карты
    Замеры NAS не приведеныони зависят от дисков, сети и содержимого библиотеки. В обзоре вместо чисел дан протокол, по которому вы получите свои

    Как обновляться дальше

    Обновления образов забираются вручную. Порядок обратный привычному: docker compose pull сам версию больше не поднимает. 

    # 1. в клоне: python3 scripts/check_image_updates.py
#    поднять теги, прочитать changelog, смержить
# 2. на NAS:
cd /volume1/docker/hh-homelab
git pull
cd media && sudo docker compose pull && sudo docker compose up -d

    Полный порядок с проверкой локальных правок — в чек-листе медиа-стека, шаги 10.2 и 10.3, и в чек-листе Home Assistant, шаги 11.3 и 11.4. Откат — обычный git revert: версии лежат в репозитории, а не в памяти.

    Как выпускается версия

    Actions → Выпуск → Run workflow, ввести номер вида 1.2.3. Дальше всё само: тег, релиз и его описание. Руками в терминале ничего делать не нужно.

    Прежде чем что-то создать, workflow отказывается работать, если:

    • номер не похож на X.Y.Z — v1.0.0 и 1.0 не пройдут;
    • такой тег уже есть — выпуск не перевыпускают;
    • на этой странице нет раздела с такой версией либо в шапке значится другая. То есть выпустить версию, которую забыли описать, нельзя;
    • не проходит хоть одна проверка репозитория. Они прогоняются заново, а не берутся на веру по прошлому зелёному прогону.
    Сначала вхолостую. У запуска есть галка «Только проверить»: все сверки пройдут, но ни тега, ни релиза не появится. Стоит нажать её первой, если выпускаете нечасто и не помните, что именно проверяется.
    Состав выпуска не пишется руками. Таблица версий собирается из самих compose.yaml в момент выпуска, поэтому описание релиза физически не может разойтись с тем, что закреплено в конфигурации. Ровно та же мысль, что и в остальных проверках: всё, что может тихо разойтись, сверяется машиной.

    Что осознанно не сделано

    Kubernetes, 4K-библиотека, аппаратное транскодирование и локальный доступ Алисы — с поводами и разбором в дорожной карте, раздел «Сознательно не делаем». Смысл не в том, чтобы закрыть тему, а в том, чтобы через полгода не проходить те же рассуждения заново.
