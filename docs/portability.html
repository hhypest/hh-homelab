Другие платформы

Чек-листы написаны под Synology DS725+, но привязано к нему меньше, чем кажется. Ниже — что переносится без правок, что переписывается в .env, и чего в вашей системе не окажется вовсе. Отдельно — почему compose остаётся источником истины, даже если разворачивать вы будете через Terraform или Ansible.

меняется .env переносится всё остальное пути в compose относительные

Соседние документы: медиа-стек · развёртывание Home Assistant · обзор проекта.

    Раздел 0

    Что переносится, а что нет

    К Synology привязана документация, а не конфигурация. В обоих compose.yaml нет ни одного абсолютного пути к состоянию сервисов — только относительные ./config/<сервис>, которые Compose разрешает от каталога самого файла. Поэтому клон переносится куда угодно и поднимается там же, без правки путей.

    ЧтоПереноситсяПочему
    media/compose.yaml, homeassistant/compose.yaml да, без правок всё машинозависимое вынесено в .env, значений по умолчанию нет намеренно
    .env переписывается это и есть тот файл, ради которого затевалась вся параметризация
    homeassistant/config/ да, в любую установку Home Assistant пакеты, автоматизации, шаблоны и дашборд не знают, в чём запущен HA
    pachca/*.liquid да шаблоны живут на стороне Пачки и от платформы не зависят вовсе
    scripts/, tests/, CI да проверяют содержимое репозитория, а не хост
    Пути вида /volume1/… в тексте нет это раскладка томов DSM
    PUID=1026, PGID=100 нет 1026 — первая учётная запись DSM, на других системах номер другой
    Container Manager, Git Server, Hyper Backup, Планировщик задач нет пакеты DSM; замены — в разделе 5
    sudo перед каждым docker нет в DSM иначе нельзя; на обычном Linux решается членством в группе docker
    Почему это вообще получилось. Ровно из-за двух решений, принятых по другим причинам: состояние сервисов монтируется относительными путями, а машинозависимые значения живут в .env без значений по умолчанию. Первое делает клон самодостаточным, второе — заставляет docker compose up упасть с именем недостающей переменной вместо тихого запуска с чужими настройками.
    Два абсолютных пути всё же есть — и оба в homeassistant/compose.yaml. Это не состояние сервисов, а ресурсы хоста, но именно они ломаются на чужой системе первыми:
    МонтируетсяЗачемКогда сломается
    /etc/localtime время хоста внутрь контейнера на системах, где этого файла нет. Строку можно просто убрать: часовой пояс и так задан через TZ
    /var/run/docker.sock прокси читает через него Docker API в rootless-режиме сокет лежит в $XDG_RUNTIME_DIR/docker.sock, у Podman — свой путь. Проверьте docker context inspect и подставьте фактический
    Раздел 1

    Минимум, который надо переписать

    Шесть величин. Всё остальное в образцах .env.example платформенно-нейтрально.

    PUID и PGID

    Узнаются одной командой — от того пользователя, под которым вы ведёте стек: 

    id
    СистемаЧто обычно
    Synology DSM1026:100 — первая учётная запись и группа users
    Обычный Linux1000:1000 — первый созданный пользователь
    Unraidв шаблонах принято 99:100 (nobody:users)
    QNAP, TrueNAS и прочиесмотрите id на месте, единого значения нет
    Эти же числа должны владеть каталогами. Корень библиотеки, каталоги состояния и сам клон — всё принадлежит PUID:PGID. Разъедутся — контейнеры молча потеряют запись, и выглядеть это будет как «загрузки встали», а не как проблема с правами.

    MEDIA_ROOT

    Единственное требование к нему платформенно-независимо: торренты и библиотека должны лежать на одной файловой системе, иначе Radarr не сможет импортировать хардлинком и начнёт копировать файлы. Проверяется сравнением номера устройства: 

    stat -c '%d %n' /путь/torrents /путь/media

    Первое число совпало — одна файловая система, хардлинки будут.

    Классическая ловушка Unraid. Пользовательские шары (/mnt/user/…) и диски напрямую (/mnt/disk1/…) — это разные пути к одним файлам. Смонтируете загрузки одним способом, а библиотеку другим — stat покажет разные устройства, и импорт пойдёт копированием. Оба каталога должны быть под одним и тем же префиксом.

    NAS_HOST

    Адрес машины в домашней сети. Из него собирается JELLYFIN_PublishedServerUrl — тот адрес, который Jellyfin сообщает клиентам, чтобы приложения на телевизоре и приставке находили сервер сами.

    Ломается тихо и не там, где ищут. Оставите чужой адрес из образца — Jellyfin поднимется, веб-интерфейс откроется, и всё будет выглядеть рабочим. Не заработает только автообнаружение: приложение на телевизоре получит адрес, по которому никого нет. Адрес должен быть постоянным — закрепите его за машиной в DHCP роутера.

    Порты, BIND_ADDR и TZ

    DSM занимает 5000 и 5001, поэтому ни один сервис в образце на них не назначен. У вашей платформы заняты другие: у Unraid — 80, у Container Station и многих панелей — 8080. Проверьте до первого запуска: 

    ss -tulpn | grep -E ':(9080|9696|7878|8191|8096|5055|6881|7359|8123|2375)\s'
    Два номера из этого списка легко упустить. 6881 — порт раздачи qBittorrent, публикуется сразу в TCP и UDP. 7359 — автообнаружение Jellyfin, только UDP. Оба задаются в .env (QBITTORRENT_TORRENT_PORT и JELLYFIN_DISCOVERY_PORT), и если проверять только веб-интерфейсы, конфликт вскроется уже при docker compose up.
    check_ports.py ловит не это. Он сверяет порты между сервисами внутри compose-файлов и найдёт, если вы назначили один номер дважды. Занят ли порт на вашем хосте — он не знает и знать не может. Это остаётся за командой выше.

    BIND_ADDR=0.0.0.0 публикует порты во всю локальную сеть, 127.0.0.1 — только на самом хосте, если впереди стоит обратный прокси. TZ указывается дважды, в обоих .env: это отдельные compose-проекты, и в соседний каталог Compose не заглядывает.

    Раздел 2

    Платформы по отдельности

    Обычный Linux с Docker Engine

    Самый простой случай: чек-листы применимы дословно, кроме sudo и путей. Добавьте себя в группу docker — и sudo из всех команд уходит: 

    sudo usermod -aG docker "$USER"
# перелогиниться, иначе членство не подхватится
docker compose version
    Compose должен быть второй версии. В командах везде docker compose (плагин), а не docker-compose (отдельный скрипт первой версии). На первой версии часть синтаксиса в файлах не разберётся.

    Xpenology

    Это тот же DSM, поэтому оба чек-листа применимы дословно, включая номера учётных записей и раскладку /volume1. Два отличия стоит держать в голове.

    Аппаратное транскодирование, скорее всего, появится. У «плюсовых» Synology на AMD Ryzen нет встроенного видеоядра, поэтому в media/compose.yaml не проброшен /dev/dri. На типичном железе Xpenology процессор Intel со встроенной графикой, и устройство есть. Проверить и включить:
    ls -l /dev/dri

    Есть вывод — добавьте в сервис jellyfin:

        devices:
      - /dev/dri:/dev/dri
    Обновления DSM на неоригинальном железе — отдельный риск. Загрузчик и драйверы сетевых карт переживают не каждое обновление, а перезагрузка после неудачного обновления может не подняться вовсе. Резервная копия конфигурации до обновления здесь не формальность.

    QNAP и другие NAS с оболочкой над Docker

    Container Station умеет разворачивать compose-файлы, но у оболочек есть общая черта: они хранят свою копию настроек и способны переписать контейнер мимо ваших файлов. Надёжнее поднимать стек из командной строки — ровно как в чек-листах, — а оболочку использовать только для просмотра.

    Пути и номера смотрите на месте. Раскладка томов у QNAP другая (/share/…), номера учётных записей тоже. Оба значения — это две строки в .env и ни одной правки в compose.

    Docker Desktop на macOS и Windows

    Годится проверить конфигурацию, но не для боевой установки. Home Assistant запущен с network_mode: host, и на не-Linux Docker Desktop это ведёт себя иначе: контейнеры работают в виртуальной машине, поэтому обнаружение устройств по mDNS и SSDP в домашней сети не работает так, как в чек-листе. Заодно теряет смысл NAS_HOST: адрес, который Jellyfin сообщает клиентам, указывает внутрь виртуальной машины, и приложения на телевизоре по нему не придут.
    Раздел 3

    Home Assistant: контейнер или HA OS

    Home Assistant ставят четырьмя способами, и конфигурация из этого репозитория переносится во все, а compose-файл — только в один. Но переносится не дословно: в config/ есть адреса, верные лишь пока Home Assistant делит петлю с медиа-стеком.

    Как поставлен HAЧто берём из репозитория
    Контейнер (как здесь) всё: compose.yaml, .env, config/
    HA OS, Supervised, Core только config/ — пакеты, автоматизации, шаблоны, дашборд, secrets.yaml
    Адресов восемь, и подстановки переменных в них нет. Это YAML и Python Home Assistant, а не compose: значения из .env в них не попадают. Все восемь написаны как 127.0.0.1 и верны ровно до тех пор, пока Home Assistant работает в host-сети на той же машине, что и медиа-стек. Перенесёте HA — каждый будет указывать на чужую петлю.
    ГдеСколькоКуда указывает
    packages/monitoring.yaml шесть по одной проверке на сервис медиа-стека: 9080, 9696, 7878, 8191, 8096, 5055
    packages/docker.yaml один docker-socket-proxy, 2375. Тот же номер отдельно лежит в DOCKERPROXY_PORT — правятся оба
    packages/media_tv.yaml один Jellyfin, 8096 — сенсор «продолжить просмотр»
    bin/docker_state.py значение по умолчанию 2375, но переопределяется переменной окружения DOCKER_PROXY_URL — единственное место, где правка файла не нужна

    Найти их все на своей копии:

    grep -rn '127\.0\.0\.1' homeassistant/config --include='*.yaml' --include='*.py'
    Чем это проявится, если забыть. Сенсоры уйдут в «недоступно», а Пачка исправно пришлёт тревогу про живые контейнеры — то есть выглядеть будет как поломка медиа-стека, хотя сломан только адрес в конфигурации Home Assistant. Это тот случай, когда тревога хуже молчания: она уводит от причины.
    Почему сокет всё равно не пробрасывается напрямую. Довод не зависит от платформы: доступ к docker.sock равносилен root на хосте. Прокси отдаёт только те методы API, которые нужны для чтения состояния контейнеров. При переносе на другую систему это свойство стоит сохранить, каким бы способом вы прокси ни запустили.
    Раздел 4

    Terraform, Ansible и почему compose остаётся источником истины

    Не переписывайте compose в ресурсы Terraform. Соблазн понятен, но обмен неудачный. Вы потеряете порядок запуска, подстановку из .env и общую сеть — а главное, все проверки репозитория станут декоративными: CI разворачивает docker compose config на образцах .env.example и сверяет порты именно в compose-файлах. Разворачиваться при этом будет что-то другое, и расхождение вы заметите не в CI, а на живом сервисе.

    Разделение, которое работает:

    ИнструментЕго зона
    Terraform хост целиком: машина, диски, сеть, правила межсетевого экрана, DNS-запись. Стек на готовый хост приезжает через cloud-init или provisioner — тем же git clone и docker compose up -d
    Ansible ближе по задаче: роль ставит Docker, клонирует репозиторий, кладёт .env из хранилища и вызывает docker compose up -d. Между хостами различается ровно один файл — тот самый .env
    Compose что именно запущено и как связано. Остаётся здесь и остаётся единственным описанием
    Секреты берите из хранилища своего инструмента. .env перечислен в .gitignore и не должен появиться ни в репозитории, ни в state-файле Terraform, который тоже хранит значения открытым текстом. Ansible Vault, SOPS, переменные окружения CI — годится любое, кроме коммита.
    Проверки репозитория остаются полезными и у вас. validate_config.py, validate_entities.py, check_ports.py и тесты читают файлы, а не хост, — значит работают в вашем CI без единой правки. Если вы форкнули репозиторий и меняете конфигурацию под себя, это единственное, что подскажет про сломанную ссылку на сущность или разъехавшийся порт до того, как это увидит Home Assistant.
    Раздел 5

    Чему нужна замена

    Механизмы DSM, на которые чек-листы ссылаются между делом, и чем они закрываются на обычной системе.

    В DSMЧем заменитьЗамечание
    Container Manager docker compose из командной строки в чек-листах это и так основной путь, оболочка нигде не обязательна
    Пакет Git Server ради команды git пакетный менеджер системы странность только DSM: там базовой команды git нет
    Hyper Backup restic, borg, rsync копировать нужно config/ обоих стеков и оба .env; библиотека восстанавливается скачиванием, настройки — нет
    Планировщик задач DSM cron или таймеры systemd —
    Индексатор Synology ничего каталоги @eaDir не появятся; строка в .gitignore просто не понадобится
    sudo перед docker группа docker см. раздел 2
    Чего в этом документе намеренно нет. Пошаговых инструкций под каждую платформу: они устареют быстрее, чем их успеют прочитать, и проверить их на живом железе я не могу. Здесь только то, что следует из устройства самого репозитория, — а дальше работают оба основных чек-листа, с поправкой на пять величин из раздела 1.
